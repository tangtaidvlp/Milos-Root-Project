Three kinds of feedback

The first step of /speckit-iterate is to sort each item. The fix depends on whether the code, the spec, or your mind is what changed.

KindExampleWhat it meansFix
BugThe Save button does nothingThe code doesn't do what the spec says/speckit-debug: failing test, then fix. Spec unchanged.
Spec gapnewThe routine form was built without a mockupThe spec never said, so Claude guessedAdd the decision to spec.md, adjust the plan, add tasks, build them
Change of mindnewSeeing it, you want a drawer, not a modalThe spec was followed, but you now want something elseChange spec.md and record why, then rework the affected tasks
New scope"Also add sharing with friends"Not part of this featureStart a new feature with /speckit-feature-init

Where each round is recorded

specs/F###-*/feedback.mdOne section per round: each item, its kind, the decision, and what changed. Proposed.
spec.md → ## ClarificationsA new ### Session YYYY-MM-DD for each round that changes the spec, so clarify never asks again.
tasks.mdNew tasks are added at the end, never rewritten, so you can see what came from feedback.
resources/Approved wireframes and mockups live here and become the design reference for the spec.
