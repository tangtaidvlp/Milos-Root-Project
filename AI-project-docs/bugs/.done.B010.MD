# B010: No per-user AI rate limit, and AI calls can hang for many minutes

- **Found**: 2026-11-24, E001 (F013 iteration review)
- **Severity**: High. One user can run unlimited Gemini calls (cost, abuse), and a slow or failing provider ties up requests for minutes. The constitution requires timeouts and per-user rate/cost limits on AI calls (Principle V, Principle IV "AI endpoints MUST be rate limited").
- **Where**: `ms-personal-routine-manager`: every AI entry point (`AIController` 4 chats, reflection feedback, goal save review in `PersonalGoalService`); Gemini client from `spring-ai-starter-model-google-genai` 2.0.0

## What happens

- **No rate limit:** nothing limits how many AI calls a user makes. Since F013, every goal save is an AI call too.
- **No timeout:** the Gemini `Client` is built by Spring AI's auto-configuration with no HTTP timeout (there is no property for one).
- **Long retries:** with no `RetryTemplate` bean, the chat model uses `RetryUtils.DEFAULT_RETRY_TEMPLATE`, which retries a transient failure 10 times with delays of 2s, 10s, 50s, then 3 min each. One request can hang for over 20 minutes.

## Reproduction

- **Rate limit:** send 100 chat messages in a row for one user. All of them reach the AI.
- **Timeout:** make Gemini slow or unreachable. The request waits on retries instead of failing fast.

## Expected

- Per-user limits on AI calls, set in config. Over the limit → 429 with the `ApiError` body and a friendly message; the AI is not called and nothing is stored.
- Each AI call has a timeout from config, with at most a short retry. A timeout ends as 503 "Buddy is unavailable" (B009).

## Notes

Single EC2 instance, so an in-memory limiter is enough for now.
