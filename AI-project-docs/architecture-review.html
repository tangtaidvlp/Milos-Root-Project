Routine Manager Architecture

A React single-page app talks to one Spring Boot API. The API stores everything in PostgreSQL and calls Gemini for the Buddy chat. Gemini can call back into the API through tool methods to edit routines. Everything below comes from the code and config in the repo. Where the repo doesn't say how production really runs, the open questions at the end list what to confirm.

1 · Runtime

What runs where

This is production as the frontend build sets it up. The SPA is static files on GitHub Pages. Every API call leaves the browser for the host named in VITE_API_BASE_URL in .env.production, which is a tunnel address.

2 · Backend

Inside the API

The API is a classic layered Spring app: controllers, then services, then repositories. Two things don't fit the plain stack. A midnight scheduler writes routines without any HTTP request. Gemini's tool calls come back into the routine services.

3 · Request flow

One Buddy message on the Today page

This is the most involved request in the system. It spans one HTTP call, at least two Gemini round trips, writes from inside a tool call, and an async job after commit.

4 · Data

Domain model

Every row hangs off a User. Plans flow left to right: a default routine is the template, a daily routine is one dated copy, and a reflection records what really happened that day.

5 · Frontend

Inside the SPA

There is no global state library. App.tsx holds auth state and route guards, and each feature folder has its own api/, components/ and hooks/. On load the app calls POST /auth/refresh with the cookie to sign in silently.

Structure

  • app/App.tsx: HashRouter routes, auth state, guards
  • lib/api.ts: apiRequest fetch wrapper with credentials: 'include'
  • features/: auth, onboarding, daily, default-routine, reflection, profile, settings, palette, walkthrough, analytics (placeholder)
  • components/layout/: AppShell, sidebar, page header
  • styles/tokens.css: every colour, both themes, enforced by tests

Contracts with the backend

  • Settings keys are duplicated in settingsSchema.ts and UserSettingsRegistry
  • Palette ids come from GET /api/v1/task-palette at runtime
  • Types like DailyTask are hand-written to match the backend; there is no generated client or OpenAPI spec
  • Theme and board zoom are account-level, saved with PATCH …/settings
6 · Delivery

From push to production

Each repo deploys on every push to main. Neither pipeline runs a test, and the backend deploy step doesn't pass any configuration to the container.

8 · Review

Findings

These are ordered by risk. Each one cites the file it comes from. The fixes are proposals for you to accept, change or ticket.

1 critical3 high4 medium4 low
  1. Critical

    F1 · A Gemini API key is committed to a public repo

    AI-project-docs/AWS-Architect.MD contains a full java -DGEMINI_API_KEY=… command with a real key. It was committed in e22c3d2, and the root repo on GitHub is public.

    Fix: revoke the key in Google AI Studio today and issue a new one. Then remove the line from the file. Once the key is revoked, rewriting git history is optional.

  2. High

    F2 · The deployed container starts on the local profile

    The CI step runs docker run -d --name routine-backend -p 8080:8080 … with no -e or --env-file, and the Dockerfile sets no ENV. As written, the app runs as local: authentication off, ddl-auto: update, and a database URL of localhost:5469 inside the container. It also has no GEMINI_API_KEY.

    Fix: pass --env-file /etc/routine/prod.env with SPRING_PROFILES_ACTIVE=prod and the secrets. If the host already injects these some other way, write that down in the repo.

  3. High

    F3 · Security is off unless a profile turns it on

    SecurityConfig permits every request when the profile is local or fast, and local is the default. Any deploy that forgets the profile is fully open. F2 is exactly that mistake.

    Fix: make the default secure. Either remove the default profile so the app fails to start without one, or make auth bypass an explicit property, such as app.security.disabled=true, set only in application-fast.yml and application-local.yml.

  4. High

    F4 · The JWT signing key is generated at startup

    Jwts.SIG.HS256.key().build() runs on boot, so every deploy or restart signs everyone out and two instances can't share sessions. The constitution already requires the key to come from a secret.

    Fix: read a base64 key from an env var, for example APP_JWT_SECRET, and fail to start if it's missing in prod.

  5. Medium

    F5 · Nothing tests a change before it ships

    The backend runs build -x test, the frontend runs only pnpm build, and both deploy straight from main. 32 of the 76 backend tests need a local Postgres. Of 11 backend test classes, 9 boot the whole app context.

    Fix: add a test job that must pass before deploy: Vitest plus ./gradlew test with Testcontainers. Move the Postgres-dependent classes onto a shared BaseIntegrationTest.

  6. Medium

    F6 · Four edge setups in the repo, none marked as the real one

    The repo has four. The frontend build points at a tunnel host. nginx.conf serves milos-ui-0.0.1 on :4173 and proxies /api/. application-prod.yml says Caddy terminates TLS. The frontend CLAUDE.md describes S3 + CloudFront. Prod CORS also falls back to the placeholder app.example.com.

    Fix: pick one, delete or archive the others, and record it in AWS-Architect.MD (without secrets).

  7. Medium

    F7 · Schema changes are hand-run SQL

    Prod uses validate, and every feature since F004 ships a db/*.sql that someone must run before the new image starts. Local and SIT use update, so a script with a mistake can still pass locally.

    Fix: adopt Flyway, as the constitution targets, with the existing scripts as baseline migrations. Run local and test databases with validate too.

  8. Medium

    F8 · The design assumes exactly one server

    Three things assume one instance: the in-memory JWT key, the @Scheduled midnight job and the in-process @Async compaction. A second instance would break sessions and spawn every user's day twice. That's fine on one EC2 box, but it's a hidden limit.

    Fix: nothing is needed now. Before scaling, fix F4 and add a lock such as ShedLock around the job.

  9. Low

    F9 · Two AI tool mechanisms

    The legacy AiRoutineFunctions function beans sit beside the @Tool classes that Gemini actually uses. Rule changes have to be checked in both.

    Fix: delete AiRoutineFunctions after confirming nothing registers it.

  10. Low

    F10 · Dockerfile hard-codes the jar version

    COPY build/libs/routinemanager-0.0.3-SNAPSHOT.jar fails once the version changes.

    Fix: set a fixed bootJar archive name, or copy build/libs/*-SNAPSHOT.jar.

  11. Low

    F11 · Hand-kept API contract

    Frontend types, settings keys and palette hints are kept in sync by hand. Two URL-building patterns coexist in the frontend, and context/Auth.ts is a dead duplicate.

    Fix: consider springdoc OpenAPI plus a generated TS client. In the meantime, delete Auth.ts and standardise on toAbsoluteApiUrl.

  12. Low

    F12 · Shared UI lives inside one feature

    EditingBoard, BuddyChat, TaskEditModal and FabButton live in features/onboarding/components/, and daily, default-routine and reflection import them across features.

    Fix: move them to src/components/ in a refactor-only change.

9 · To confirm

Open questions

The repo can't answer these. The answers change how serious F2 and F6 are.

  1. Where does the tunnel host in .env.production point: the EC2 container, or a machine at home?
  2. Does the EC2 host set SPRING_PROFILES_ACTIVE, the datasource and GEMINI_API_KEY somewhere outside the repo, for example in a systemd unit or a Docker daemon config?
  3. Whose midnight does DailyTaskSpawningJob use? 0 0 0 * * ? runs in the server's time zone, which is usually UTC on EC2, and LocalDate.now() reads the same zone. A user in UTC+7 would get their new day at 07:00.
  4. Is the Nginx/EC2 setup in nginx.conf still meant to happen, or has GitHub Pages replaced it?
